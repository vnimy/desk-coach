# 日程提醒服务（service.py）

## 一、为什么要有服务这一层

原本的形态是「系统调度器按多个触发器到点拉起脚本弹窗」。这能跑，但有三个说不通的地方：

1. **开关不统一** —— 停提醒要禁用系统任务，一键开关要另写脚本。
2. **页面无法联动** —— 日程表是静态 HTML，上面的按钮只能链到 `.bat` 文件，浏览器点开还会弹一次安全确认，体验很差。
3. **没有运行态** —— 除了系统任务列表，无法回答「现在到底会不会弹」这个问题。

服务化之后，这三件事合成一件：**启动服务 = 提醒功能生效，停止服务 = 提醒功能整体停用**。
提醒时间由服务自己的定时线程负责，系统任务退化为一个「登录时把服务拉起来」的角色。

## 二、职责划分

| 文件 | 职责 |
|---|---|
| `scripts/service.py` | 常驻壳：HTTP 接口 + 内置定时线程 + 进程生命周期 + **页面渲染** |
| `scripts/reminder.py` | 引擎：读 plan/state、渲染弹窗、匹配日程。既能被服务调用，也能单独命令行使用 |
| `assets/schedule-template.html` | **日程表页面模板**（唯一一份，与服务同处技能包） |
| `assets/winform.ps1` | Windows 弹窗渲染 |

服务通过 `sys.path` 直接 import `reminder`，复用它的 `load_plan` / `load_state` / `check_active` / `deliver`，
不重复实现任何业务逻辑。

## 三、页面渲染（内容不再重复维护）

**页面不是静态文件，而是服务在每次请求时渲染出来的。**

```
GET /  →  render_page(plan_path)
          ├─ 读技能包里的 assets/schedule-template.html
          ├─ 读 plan.json（load_plan 展开动作引用）
          ├─ 替换 __TITLE__
          └─ 把 plan 注入到 window.__PLAN__ = null; 这一行
```

好处与要点：

- **改 plan 刷新即见**，不需要重启服务 —— 因为每次 GET 都重新读盘
- **页面没有第二份副本**。早期形态是每个用户一份手写 HTML，内容与 plan 各存一份，
  必然失同步（用户曾因此看到「页面上有 11:15 但到点不弹」）
- 模板里用 `window.__PLAN__ = null;` 作为**注入点**：服务替换它为真实数据；
  以 `file://` 直接打开时保持 `null`，页面据此回落到 `/api/plan`
- 注入 JSON 时把 `</` 转义成 `<\/`，防止数据里的 `</script>` 提前闭合脚本块

页面顶部三张数据卡里的第一张（时间点总数）是**算出来的**，不写死在配置里，
配 `{"auto": "count"}` 即可。

## 四、内置定时器

`Scheduler` 是个 daemon 线程，每 **15 秒**轮询一次（`POLL_SECONDS`）：

1. 算出当前分钟数，逐个 slot 比对；命中条件是 `0 <= 当前 - 目标 <= 容差(5 分钟)`
   —— 只看「刚到或刚过」，不看未来，所以服务在 10:35 启动不会把 10:30 那条补弹出来。
2. **跳过 `manual: true` 的 slot** —— 这类时间点不参与自动调度，只能由用户在页面上手动点开。
3. 命中后查 state 判断是否该弹（总开关 → 单环节关闭 → 暂停）。
4. 记录到 `fired.json`，**按日期分桶**，防止服务重启后同一时刻重复弹。文件只保留最近 3 天。
5. 用子进程拉起 `reminder.py render --plan X --slot <id>`，不阻塞轮询。
6. 非生效星期直接跳过。

### 自动 vs 手动

| | 自动（默认） | 手动（`manual: true`） |
|---|---|---|
| 到点自动弹 | 会 | 不会 |
| 页面上点击弹 | 能 | 能 |
| 接口 `/api/fire` | 能 | 能 |
| 受 `disabledSlots` 约束 | 受 | 受 |

设计意图：一套日程里往往有「骨架」和「加分项」。骨架必须到点提醒（否则会忘），
加分项则不该打扰用户 —— 但想练的时候得能一键调出来。于是把它们都放进 plan，
用 `manual` 区分是否自动，页面上一律可点。

### 弹窗重叠策略

`OVERLAP_POLICY = "ignore"`（默认）：上一个弹窗没关就跳过新的。

这对应原系统任务的 `MultipleInstances IgnoreNew`。代价是"忘关窗 = 后续静音"，
好处是不会在屏幕上叠一摞窗口。要改成允许叠放就把这个常量改成 `"stack"`。

## 五、HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | **日程表页面**（用技能模板 + plan 数据实时渲染） |
| GET | `/api/plan` | 展开后的 plan，供以 `file://` 打开的页面回落使用 |
| GET | `/api/status` | 服务与提醒状态（前端靠它渲染开关区） |
| GET | `/api/ping` | 存活探测 |
| POST | `/api/pause` | 暂停本日全部提醒 |
| POST | `/api/resume` | 恢复提醒 |
| POST | `/api/disable?id=1030` | 永久关闭某个环节 |
| POST | `/api/enable?id=1030` | 重新开启某个环节 |
| POST | `/api/fire?id=1030` | **立即弹出该环节的提醒框**（页面上点击时间点走这个） |
| POST | `/api/reload` | 空操作，语义占位（plan 与 state 每次操作都重新读盘） |

`/api/fire` 的判定**与自动调度不同**：

- **暂停中（`pausedUntil`）不拦截** —— 用户是主动点开的，说明当下就想练
- **被永久关闭（`disabledSlots`）会拒绝** —— 避免"我明明关掉了它怎么又弹"
- 找不到 id 时返回可用的 id 列表，便于排查

`/api/status` 的每个 slot 会带 `manual`（是否自动弹）、`off`（是否被关闭）、`active`（综合判定）三个字段，
前端据此渲染「自动 / 手动」标签和开关状态。

**CORS 是必须的**：页面可能以 `file://` 直接打开，此时对 `http://127.0.0.1` 发的是跨源请求
（`Origin: null`），不放开 `Access-Control-Allow-Origin` 会被浏览器拦掉。

用 POST 且不带自定义头，属于简单请求，不会触发 OPTIONS 预检；`do_OPTIONS` 仍然实现了，以防万一。

只监听 `127.0.0.1`，不对外网暴露。

## 六、进程生命周期

### 启动

`service.py start` 优先**用计划任务托管进程**：

```
schtasks /end  /tn CoreReminder     # 清掉可能存在的旧实例
schtasks /run  /tn CoreReminder     # 由系统服务拉起
```

为什么不用 `subprocess.Popen(DETACHED_PROCESS)`：从 shell 里 spawn 的后台进程，在受限环境
（带 Job Object 的终端、某些 CI/沙箱）里会随父进程的作业关闭而被回收。交给任务计划程序则完全脱钩。

计划任务不存在或被安全策略拦下时，自动降级为直接 spawn。加 `--no-task` 可强制走降级路径。

启动后等端口真正可连（最多 15 秒），再用 `netstat -ano` **从端口反查真实 pid** ——
因为进程是计划任务拉起的，拿不到 Popen 句柄，反查比依赖句柄可靠。pid 记在 `service.json`。

### 停止

`taskkill /PID <pid> /F`，同时 `schtasks /end` 结束任务实例（否则任务会卡在"正在运行"状态，
下次启不动）。

## 七、前端联动

日程表页面底部有两个按钮和一个环节列表，全部走 `fetch` 调接口：

- 顶部状态条：绿点「服务运行中」/ 灰点「服务未运行」，未运行时按钮置灰并提示启动命令
- 「暂停今日提醒」/「恢复提醒」：按 `pausedUntil` 自动互斥置灰
- **每个时间点一行「胶囊」，由两部分组成**：
  - **主体**（圆点 + 时间 + 动作名 + 自动/手动标签）：点击 → `/api/fire?id=<id>`，**立即弹出这条提醒框**，用来随时补做
  - **右侧 `●` / `○` 小按钮**：点击 → `/api/disable|enable?id=<id>`，单独开关这个环节
    （`●` 绿=开启，`○` 灰=关闭；整体变淡表示已关闭）
- 操作结果用页面内 toast 提示，不再跳转

页面用 `location.protocol` 判断自己是怎么被打开的：由服务托管时用相对路径，
直接双击本地文件时回落到 `http://127.0.0.1:8768`（端口硬编码，改端口要同步改页面）。

时间轴上的徽标也对应这套语义：绿色「自动弹」= 到点自己弹，蓝色「手动补做」= 只在页面点开。

## 八、相关字段

`plan.json` 里与服务有关的字段：

| 字段 | 说明 |
|---|---|
| `port` | 服务端口，缺省 8768 |
| `scheduleUrl` | 弹窗「日程表」按钮打开的地址，缺省按 `port` 推 `http://127.0.0.1:<port>/` |
| `title` / `subtitle` / `page` | 页面标题、副标题、页面级内容（分区标题、原则、面板、提示等）。见 plan-schema |

`state.json` 的 `taskName` 被 `service.py` 用来定位计划任务（start/stop 都要用到）。

**页面已不再依赖本地 HTML 文件** —— 早先的 `schedule` 字段（指向一个手写 HTML）在服务化后
已无用途，可留空。页面唯一来源是技能模板。

## 九、排查

| 现象 | 查看 |
|---|---|
| 服务起不来 | `<plan 目录>/service.log` |
| 到点没弹 | `service.log` 里有没有「跳过」记录；再看 `fired.json` 当天是否已记 |
| 页面按钮点了没反应 | 服务是否在跑（状态条应显示绿点）；F12 看是否被 CORS 拦 |
| 服务反复被杀 | 检查计划任务的执行时限是否为「不限时」（`ExecutionTimeLimit` 设为零） |
